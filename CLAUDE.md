# CLAUDE.md — meteo-guadalentin

## Project Overview

**Meteo Guadalentín** is a real-time weather monitoring and agricultural risk dashboard for the Guadalentín valley (Murcia, Spain), hosted at `meteoguadalentin.com` via GitHub Pages.

It aggregates data from ~91 personal weather stations (Weather Underground PWS) plus AEMET reference stations, calculates agricultural disease risk (DSV — Disease Severity Value, Gubler-Thomas formula), and serves an interactive map dashboard updated every 5 minutes automatically.

**No server, no database, no external Python dependencies.** Everything is Python stdlib + static JSON files + GitHub Actions.

---

## Architecture

```
GitHub Actions (cron: */5 * * * *)
        │
        ▼
check_historial.py  ──(fails)──►  fix_historial.py
        │(OK)
        ▼
mapa_totana.py
  ├─ Fetch ~91 WU stations (25 concurrent threads)
  ├─ gestionar_historial()         → history_24h.json   (24h rolling)
  ├─ gestionar_historial_agricola() → historial_agricola.json  (14-day)
  ├─ generar_json()                → data.json          (current snapshot)
  └─ generar_html()                → index.html         (full SPA, data embedded)
        │
        ▼
git commit + push → GitHub Pages serves static files
```

The SPA reads all data from the embedded JSON in `index.html` at load time. `data.json`, `history_24h.json`, and `historial_agricola.json` are also served as separate files (consumed by external tools or L&A Agrícola).

## Python Scripts Reference

| Script | When to run | Purpose |
|--------|-------------|---------|
| `mapa_totana.py` | Every 5 min (CI) or manually | Main: fetch all stations, update all JSON outputs, regenerate `index.html` |
| `check_historial.py` | Before main run (CI) | Validates `historial_agricola.json` has ≥50 temperature entries; exits 1 if not |
| `fix_historial.py` | When check fails | Downloads last 7 days from WU and rebuilds `historial_agricola.json` |
| `rellenar_historial.py` | Once (initial setup) | Backfills 7-day WU history across all stations |
| `dsv_desde_marzo.py` | Once per season | Calculates DSV accumulation from March 1st using WU owner API |
| `inicializar_dsv.py` | Once (alternative init) | Alternative: initialise DSV using AEMET climatological data |

### Execution in CI

```yaml
python3 check_historial.py || python3 fix_historial.py
python3 mapa_totana.py
git add -A && git commit -m "Meteo $(date)" && git push
```

### Manual local run

```bash
python3 mapa_totana.py            # full update cycle
python3 check_historial.py        # validate history (exit code: 0=OK, 1=needs fix)
python3 fix_historial.py          # repair corrupted or missing history
python3 rellenar_historial.py     # one-time 7-day backfill
python3 dsv_desde_marzo.py        # one-time seasonal DSV calc
```

## Data Files

### `data.json` — Current snapshot

```json
{
  "actualizado": "DD/MM/YYYY HH:MM:SS",
  "timestamp": "ISO8601",
  "estaciones": [
    {
      "id": "ITOTAN8", "nombre": "...", "lat": 37.xx, "lon": -1.xx,
      "temp": 22.5, "tempMin": 18.0, "tempMax": 28.0,
      "humedad": 55, "lluvia": 0.0, "lluviaHora": 0.0,
      "viento": 5.2, "rachaViento": 8.1, "presion": 1013.2,
      "dewPoint": 12.3, "uv": 4, "solar": 680, "actualizado": "..."
    }
  ]
}
```

### `history_24h.json` — 24-hour rolling history

```json
[
  { "timestamp": "ISO8601", "stations": [ /* same structure as WU observations */ ] }
]
```
Trimmed to the last 24 hours on every run. Entries older than 24h are dropped.

### `historial_agricola.json` — 14-day agricultural data

```json
{
  "YYYY-MM-DD": {
    "STATION_ID": {
      "tempMax": 30.1, "tempMin": 18.5,
      "precipTotal": 0.0, "humedadAltaMinutos": 90
    }
  }
}
```
`humedadAltaMinutos`: cumulative minutes where humidity ≥ 85% (increments 15 min per update). Used in DSV calculation. Retention: last 14 days (oldest deleted when count > 14).

### `historial_dsv.json` — Disease Severity Value

Cumulative DSV per station since the start of the season (March). Each entry tracks `dsv_acumulado`, `dsv_aemet`, `dsv_wu_extra`, `ref_estacion`, and dated records.

## Station Registry (`estaciones.txt`)

One WU station ID per line. Lines beginning with `#` are comments.

Station ID format: prefix + number (e.g., `ITOTAN8`, `ILORCA23`, `IALEDO5`, `IALHAM12`). The prefix encodes the municipality.

To add a station: append its WU station ID to `estaciones.txt`. It will be picked up on the next run of `mapa_totana.py`.

### Estaciones que fallan: lista a mano y filtro automático (`filtro_estaciones.py`)

- **`estaciones_desactivadas.txt`**: una estación por línea (`ILORCA45  # motivo y fecha`). No se descarga, el riesgo no la usa (ni como vecina) y el mapa la quita también de los históricos ya guardados (`sinDesactivadas()` / `riesgoSinDesactivadas()` en el JS, al cargar `history_24h/2d/7d.json` e `historial_riesgo.json`). **Los archivos no se tocan**: quitar su línea la reactiva con todo su historial. Es más cómodo que comentarla en `estaciones.txt`, que solo deja de descargarla y no limpia lo ya guardado.
- **Filtro automático** (`filtrar_lecturas()`, se aplica a cada lectura nueva antes de guardarla): rangos físicos (`RANGOS`), rocío por encima de la temperatura, saltos imposibles respecto a la última lectura válida de la misma estación en los últimos 30 min (temperatura >10 °C, humedad >50 puntos, lluvia que sube >50 mm; bajar a 0 a medianoche es normal), temperatura a más de 9 °C de la mediana de las vecinas en 20 km (con ≥4 vecinas), y observaciones de hace más de 3 h (esas se quitan enteras). Lo malo se guarda como `null` con el motivo en `est.descartado` (el panel de la estación lo enseña; los derivados —rocío, sensación— caen con su campo) y se acumula en **`filtro_estaciones.json`** (por estación y campo: veces, primera/última vez, último valor; 7 días), que es donde mirar antes de desactivar una.
- Contrastado con las 24 h reales (oct 2026): de 12.441 lecturas descartó 426, de 5 estaciones (ILORCA124 con humedad 0 % y 0 °C, IELCHE114 a 1.100 hPa, IMULA25 con rocío de −39 °C…). Humedad mínima 3 %: IHELLN10 daba 1 % de noche en otoño. Algunas estaciones en altura dan la presión de la estación (~940 hPa), no la del nivel del mar: por eso el mínimo es 900.
- Pruebas: `python3 -m unittest test_filtro_estaciones`.

## Frontend (`index.html`)

- **Generated** by `mapa_totana.py::generar_html()` on every run — do not edit manually
- Single HTML file (~910KB) with all CSS, JS, and data embedded inline
- **Libraries (self-hosted under `vendor/`, not CDN):** Leaflet 1.9.4 (`vendor/leaflet/`) and Turf.js 6.5.0 (`vendor/turf/turf.min.js`) — previously loaded from unpkg.com/jsdelivr.net via blocking `<script>` tags in `<head>`, which made page-load time depend on those third-party CDNs' own latency (the actual cause of "a veces tarda mucho en cargar" reports). Referenced with root-absolute paths (`/vendor/...`) so they resolve the same from `index.html` and from the `public/` mirror. To upgrade a version: `npm install leaflet@X @turf/turf@Y` somewhere, copy the new `dist/leaflet.{js,css}` + `dist/images/` and `turf.min.js` over the existing `vendor/` files
- **Basemaps:** Google (relief/satellite) and Esri World Light Gray. CARTO basemaps are no longer usable — they require an API key and stamp "API KEY REQUIRED" over the tiles. `vigilarFondo()` falls back to OSM if a basemap stops responding
- **Map center:** Totana, Murcia (37.76°N, -1.53°W)
- **Features:** parameter selector (temp/humidity/precipitation/wind), time-slider playback over `history_24h.json` with 6h/12h/24h/2d/7d window buttons, opacity slider, station pop-ups with custom names, grayscale tile option
- **No time machine on the map** (removed Nov 2026): the map used to let you scrub a slider back to any past moment (6h/12h/24h/2d/7d, with playback) and, in Riesgos, filter by day the same way — repainting the whole map from a historical snapshot. That's gone; the map always shows the live/latest snapshot (`historyData[historyData.length-1]`, no more `activeData`/`CI` scrubbing). What it did — seeing how a station or a risk looked on previous days — moved into the station panel as proper charts (see **Station panel 12h trend chart** below), which is both simpler (no slider/playback state to keep in sync) and, for risk, actually shows *more* real days: the old risk day-filter was bottlenecked by `historyData`'s 24h retention, so it could only ever cover 1-2 calendar days despite `historial_riesgo.json` holding a full season
- **`history_24h.json`/`history_7d.json` are loaded on demand, not on page load**: `history_24h.json` (several MB) used to be fetched unconditionally on every page load — the actual cause of "tarda mucho en cargar" reports on top of the CDN issue fixed earlier. `asegurarHistoria24hCompleta()` now defers that fetch until a station panel is opened (needed for the 12h and days-anteriores charts); until then the map runs off the single embedded seed snapshot, kept current by the unconditional 5-minute background refresh (`actualizarDatos()` near the bottom of `generar_html()`). `history_7d.json` (`asegurarHistoria7d()`) and `historial_riesgo.json` (`cargarRiesgoHistorico()`) follow the same pattern, each fetched only the first time a station panel actually needs them
- **Menú principal lateral (☰)** (`#nav`, `irA(vista)`, `aplicarVista()`): the only way to move between the three screens — station map (home), per-town forecast (`#vp`) and rain forecast map (`#vl`). The ☰ button sits top-left on all three; it replaced the old "🔮 Pronóstico" dropdown on the map and the "← Mapa" / cross-link buttons on the other screens, which users found confusing. The open screen lives in the URL hash (`#pronostico`, `#lluvia`, none = map) via `history.pushState`, so the browser/phone back button returns to the previous screen and a link with `#pronostico` opens it directly. `actualizarPronBtn(v)` now only highlights the active entry in the menu
- **Mi zona** (`#vz`, `renderZona()`): home screen on phones (≤768 px; desktop still opens on the map), the direct answer for one place without reading the map. Places come from the GPS ("Usar mi ubicación") or the Open-Meteo geocoder and are kept in `localStorage` (`meteo_zonas`, the first one is the current; chips to switch, 🗑 to remove) — the site is static, nothing is stored server-side. Cards: warnings for the next 48 h (`avisosZona`: frost ≤2/≤0 °C, heat ≥36/≥40, gusts ≥45/≥60 km/h, rain ≥10/≥30 mm today or tomorrow, and oídio/mildiu level ≥2 from the nearest station's `riesgoData`); "¿Se puede tratar?" (`tratarZona`: now + until when, or the next ≥2 h good window, and a 24 h colour strip — same criteria as `mgPulverizar`); "Ahora" from the nearest station with data (≤25 km) and other ones ≤15 km; next 4 days, with a button that opens the meteogram for the same place (`verMeteogramaZona`). One Open-Meteo request per place, cached 30 min in memory. Re-rendered on the 5-minute data refresh. The Pronóstico tab falls back to the Mi zona place when no town was ever searched
- **«Donde estoy»** (Mi zona, `gps:true`, only one): instead of saving the position of one moment, it follows the GPS (`watchPosition`, `actualizarSeguimiento()`) only while Mi zona is on screen with it selected and the page visible. Each fix is stored; moving more than `ZONA_MOVIDO_KM` (0.3 km) re-renders everything (nearest station, warnings, forecast — the forecast cache key `clavePron()` uses ~2 km cells so small moves don't refetch); otherwise only the status line (`#vz-gps-linea`: near which station, ±accuracy, last update) is refreshed. «Guardar aquí como finca» pins the current spot as a fixed place. Several old "Mi ubicación" entries from the previous version collapse into one
- **Añadir finca tocando el mapa** (`#btn-pin`, `activarModoPin()`, map `'mapa'`/`'riesgos'` screens only): a third way to save a place in Mi zona, for a finca with no GPS to hand and no nearby town that names it well — GPS and the Open-Meteo geocoder don't cover that case. Arms a "next map click" mode (crosshair cursor, `#aviso-pin` banner with a cancel link); the click's `latlng` becomes the new `zonasGuardadas()` entry (named via `prompt()`, defaulting to the nearest station's name through `cercaDe()`), then `irA('zona')` opens Mi zona on it. Disarmed by clicking the button again, by the map click itself, or automatically by `aplicarVista()` when leaving the map/Riesgos screens. There used to be a separate `#btn-loc` (🎯 "Mi ubicación") next to it, just to centre/zoom the map on the user's GPS (`locateMe()`, still there as a helper) — removed (Nov 2026) so "where am I" isn't its own button: `activarModoPin()` now calls `locateMe()` too when arming, so the map conveniently centres near the user first (if geolocation is granted; if not, pin mode still arms the same), but you can still tap anywhere, not just your exact GPS point
- **Map attribution without the "Leaflet |" prefix** (`map.attributionControl.setPrefix(false)`): on phones the attribution control sits directly under the Leaflet layers icon in the same bottom-right corner, and the full default text ("Leaflet | © Google") didn't fit, getting clipped at the screen edge. Just the per-layer credit (already set via each `tileLayer`'s own `attribution` option) is short enough to fit; `.leaflet-control-attribution` also caps at `calc(100vw - 16px)` with an ellipsis as a backstop
- **Bottom tab bar on phones** (`#tabs`, ≤768 px): Mi zona · Mapa · Pronóstico · Lluvia, same `irA()` routing as the ☰ menu (which is hidden on phones and keeps a "Mi zona" entry on desktop). `--tabs-h` (60 px + safe area) lifts the map, the full-screen screens, the time-machine bar and the station panel above it. `#mapa` in the URL forces the map on phones
- **Riesgos tab** (`vista 'riesgos'`, `CULTIVOS_RIESGO`, `pintarBarraRiesgos()`): agricultural risks live in their own tab, out of the weather parameters (oídio/mildiu were removed from the dropdown and the phone buttons; the `<select id="ps">` keeps their options because they are still the render keys). It reuses the same Leaflet map in risk mode — legend, heat map and station panel already knew how to draw oídio/mildiu — with its own top bar (`#topbar-riesgos`): crop chips, then the crop's risks and the model description. `entrarRiesgos()` / `salirRiesgos()` remember the weather parameter (`paramMeteo`) to return to it on the Mapa tab; `render()` draws nothing in Riesgos for a non-risk parameter. Crop and risk are remembered in `localStorage`. Risks with `prox:true` have no model yet and are shown as "próximamente"; a crop with none available shows an "en preparación" card. To add a risk: compute it per station in Python (like `calcular_riesgo`, into `riesgoData` and `historial_riesgo.json`), teach `col()`/`raw()`/`leg.upd()`/the panel about it as with oídio, add it to `esParamRiesgo()`, and drop its `prox`
- **Horticultural risks (iceberg, broccoli)** (`RIESGOS_HORT`, `riesgo_hort()`, `dia_favorable()` in Python; ids `bremia`, `mildiu_cruc`, `alternaria` in `RIESGO_IDS`): rule-based, to be validated in the field. A day is favourable when the leaf was probably wet (RH ≥ 90 %) for the hours the fungus needs within its temperature band — Bremia lactucae 4 h at 5-20 °C, Hyaloperonospora 6 h at 5-20 °C, Alternaria 9 h at 18-30 °C. Level from favourable days in the last 7: 0 none, 1 one, 2 two-three, 3 four or more or the last two in a row. `hist_agri` now counts per day `h90_frio` (RH ≥ 90 % and 5-20 °C) and `h90_calido` (18-30 °C) minutes; days that existed before the counter are flagged `parcial` and estimated from `history_7d.json` (`anotar_contadores_3h`, real readings every 3 h, each worth 3 h; recomputed each run, not saved), and failing that from RH ≥ 85 % hours and the mean temperature. Snapshots in `historial_riesgo.json` carry the new keys; older days lack them and show as no data in the station panel's days-anteriores chart (today always uses the live `riesgoData`). The station panel has a generic branch (level, model details, description) for any risk other than oídio/mildiu
- **Minutes per run fix (oct 2026)**: the agricultural history added, on each 5-minute run, the time since the last `history_24h` snapshot (saved every 15 min), so every quarter hour counted twice (days with > 24 h of high humidity, which also inflated the oídio DSV). Now the minutes are the time since the previous run, stored in `estado_agricola.json`. Past days keep the inflated values; the DSV accumulated in `historial_dsv.json` too
- **Mis cultivos** (`misCultivos()`, `localStorage` `meteo_mis_cultivos`, dialog `#mc`): each user ticks what they grow. Riesgos shows only those crops (plus a «🌱 Mis cultivos ✎» chip to change them; nothing chosen = all), Mi zona shows a «Riesgos de mis cultivos» card with the level of each of their risks at the nearest station (tapping one opens Riesgos on it, `verRiesgo`), and its warnings only include medium/high risks of those crops (nothing chosen = no disease warnings, and the card invites to choose)
- **Station grouping** (`pintarMarcadores()`, all screen sizes): below zoom `AGR_ZOOM_MAX` (14) stations closer than `AGR_PX` (42 px) are merged into one larger bubble with the station count; temperature/humidity show the group mean, rain/wind/risk the maximum. Tapping it flies to its stations. Re-grouped on `zoomend` from the markers built by `render()` (`_marcadores`), without recomputing the heat map, which still uses every station. At zoom 10: 168 stations → 132 bubbles
- **Clean map on phones** (≤768 px): the parameter dropdown becomes a sideways-scrolling row of buttons (`#chips-param`, `elegirParam()`, same `<select id="ps">` + `onParamChange()`); logo, separators and the Leaflet zoom buttons are hidden (pinch to zoom). Radar and opacity are moved (`colocarControles()`, `CTRL_CAPAS`, the same DOM nodes with their listeners; moved back if the screen widens) into a bottom sheet opened with 🧰 (`#hoja-capas`). The station panel `#dp` becomes a bottom sheet at half height; tapping or dragging its handle up opens it fully, dragging down closes it
- **Precipitation layer accumulation window** (`PRECIP_VENTANAS`: 1h/12h/24h/48h, chips shown only while that parameter is active): `acumularPrecip()` sums a station's `precipTotal` (a counter that resets to zero at local midnight) across the window, treating any drop from one reading to the next as a reset rather than negative rain — this correctly handles windows spanning multiple midnights, unlike a plain first-vs-last subtraction. Windows ≤24h read from `historyData` (the full last-24h series) when the displayed moment is recent enough, else `activeData` (now just an alias for `historyData`, kept from when it tracked the map's old time machine); 48h needs `history_2d_precip.json` (a `stationID`+`precipTotal`-only projection of `history_2d.json`, far lighter to download) unless the full `history_2d.json` is already cached, fetched on demand into the shared `extData` cache and triggering a re-render when it lands. Selection is remembered in `localStorage`. `calcularPrecipTodas()` does the actual (datos, tsRef, horas) → {stationID: mm} pass once and caches it (single-slot, by reference/value equality of those three inputs) — `acumularPrecip()` is now just a lookup into it. `render()` calls it once per on-screen station (~175) with the exact same three inputs every time, so before this fix the whole history got rescanned per station per render — switching to the Precipitación parameter was measurably slower than temp/humidity/wind for exactly this reason
- **Custom station names:** `nombresPersonalizados` object in the generated JS maps station IDs to friendly display names
- **Station panel 12h trend chart:** clicking any station marker shows a compact dark-themed SVG combo chart (`graficoEstacion12h()`) below its current-conditions table — hourly temperature (line) and hourly rainfall (bars) for the last 12 hours, in both normal and oídio/mildiu risk panel modes. Sourced entirely from `historyData` (no extra fetch) via `datosHorariosEstacion()`, which reuses `acumularPrecip()` for the per-hour rain figure and applies a 40-min staleness tolerance per hour (a gap becomes a break in the line, not a stale value). Hour labels are pinned to Europe/Madrid regardless of the visitor's own timezone (`horaEnMadrid()`, same pattern as `llFechaTxt()` in the rain forecast screen). Built **lazily inside `showPanel()`**, for the one clicked station only — building it eagerly for every on-screen station on every `render()` (as it originally did) cost ~1.4s of a ~1.8s parameter switch, by far the biggest render() cost there was
- **Station panel days-anteriores chart:** below the 12h chart, a second SVG chart covers the last `DIAS_PANEL`/`DIAS_RIESGO_PANEL` (7) days — what replaced the map time machine. `pintarGraficaDiasPanel(sid, par)`, called from `showPanel()` into its own placeholder div (`#panel-grafica-dias`), picks one of two: in weather mode, `graficoEstacionDias()` (daily max/min temperature lines + a daily rain bar, from `datosDiariosEstacion()` over `history_7d.json`, 3h resolution — a coarser view than the 12h chart, not a replacement for it); in Riesgos, `graficoRiesgoDias()` (one bar per day, 0-3, colored with the same `RC`/`RL` as everywhere else, from `historial_riesgo.json` for past days and the live `riesgoData` for today, since today's snapshot isn't saved yet). Both fetches (`asegurarHistoria7d()`, `cargarRiesgoHistorico()`) are lazy and keyed off whether a panel actually needs them, same pattern as `asegurarHistoria24hCompleta()` — the placeholder shows "⏳ Cargando histórico…" and re-renders itself once the data lands, checking `PS===sid` first in case the panel moved on to a different station meanwhile
- **Forecast screens (full-screen overlays, light theme):**
  - `#vp` — per-town forecast: Open-Meteo geocoder search + a **meteogram** (meteoblue-style, `renderPronostico(dias)`, 3/7/14 days, remembered in `localStorage`): one continuous hourly time axis shared by stacked SVG panels — temperature (curve with colour fill, daily max/min, weather icons, day names with weekends in red), precipitation (mm/h bars, probability line, low/mid/high cloud strip, daily totals), spraying conditions (`mgPulverizar()`: green/yellow/red from rain now or in the next 2 h, rain probability, wind 2-12 km/h, gusts, temperature, RH), ET0 FAO with daily total + relative humidity, and wind/gusts with direction arrows. Daytime shading from `is_day`, dashed line at the current hour, and a shared cursor + tooltip (`mgActivarCursor`) with every value at that hour. Uses Open-Meteo's `best_match` model (only one with precipitation probability, cloud layers and ET0); below it, a model comparison on the same axis (hourly temperature and accumulated rain for ECMWF/ICON/GFS/AROME). On phones (≤768 px) the width fits the screen (3 days, the default there, fit without scrolling; 7/14 days scroll at ≥3 px per hour), the y-axis figures live in sticky columns on both sides (`.mg-eje`, `_ejes` + `panel()`; the right one is placed by `mgColocarEjes()` from the box width) so the scale stays visible while scrolling, and every panel folds by tapping its title (`plegarPanel`, remembered in `localStorage` `meteo_mg_plegados`; ET0 and wind start folded on phones). The old per-day cards and per-day hourly modal were removed
  - `#vl` — accumulated precipitation forecast map (`ll*` functions): ~100-point grid over Murcia (bbox 37.0-38.9 N, -3.0-0.0 E, 0.25° step) fetched from Open-Meteo per selected model, accumulated from the current hour over 24h/48h/72h/5d/7d, interpolated with Turf IDW and painted with the standard mm colour scale; plus a per-model comparison table for the valley towns and a click-anywhere multi-model popup. Selectable basemap (`LL_FONDOS`: Esri light gray / Google terrain / Google satellite) — each one is split into a base tile layer *under* the shading and a labels-and-roads layer in the `lletiq` pane *above* it, so map information stays readable over the precipitation field; an opacity slider (`llSetOpacidad`) restyles the painted cells without recomputing the interpolation. Basemap and opacity are remembered in `localStorage`. Model list, colour scale and geographic window live in `LL_MODELOS` / `LL_ESCALA` / `LL_BBOX`

To change the map layout, UI controls, or color scales: edit `generar_html()` in `mapa_totana.py`, then run the script to regenerate `index.html`.

## Coding Conventions

- **Language of code and comments:** Spanish (variable names, function names, print messages, comments)
- **Python style:** snake_case for functions and variables, UPPERCASE for module-level constants
- **No linter or formatter** — no Black, Flake8, mypy, or any config file
- **No external Python dependencies** — stdlib only (`urllib`, `json`, `ssl`, `os`, `datetime`, `concurrent.futures`, `zoneinfo`)
- **Error handling pattern:** `try/except Exception` returning `None` or empty defaults; API failures are printed and skipped, never crash the full run
- **Concurrency:** `ThreadPoolExecutor(max_workers=25)` for parallel WU station fetches
- **Timezone:** `zoneinfo.ZoneInfo("Europe/Madrid")` with fallback to `datetime.now()` for older Python

## Common Tasks

### Add a new weather station
1. Find the WU station ID (format: `I{MUNICIPALITY}{N}`)
2. Append to `estaciones.txt`
3. Run `python3 mapa_totana.py` — the station appears on the map immediately

### Repair corrupted history
```bash
python3 check_historial.py   # identify the problem
python3 fix_historial.py     # re-download 7-day history and rebuild
python3 mapa_totana.py       # regenerate all outputs
```

### Backfill history after downtime
```bash
python3 rellenar_historial.py   # downloads last 7 days for all stations
```

### Recalculate seasonal DSV
```bash
python3 dsv_desde_marzo.py      # recalculates from March 1st using WU owner API
```

### Test data integrity locally
```bash
python3 check_historial.py   # exit 0 = OK, exit 1 = insufficient data
python3 -c "import json; d=json.load(open('data.json')); print(len(d['estaciones']), 'stations')"
```
